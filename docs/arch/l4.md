# L4 — the TJS VM host

Status: **authoritative**. Describes `crates/vm` and `crates/tjs` as they
are today.

L4 is the topmost layer. It owns the TJS2 engine instance, its log
callback, bytecode compilation, the script cache and the per-frame body. It
drives the L3 compatibility surface and uses the L1 platform abstraction; it
never names L2.

```
L4  vm       TJS VM host over tjs              (topmost)
L3  compat   native classes + KAG + event adapter + plugins
L2  engine   generic game engine (layer system, audio, VFS)
L1  platform window/host, fs + archive parse, render, media
```

The VM is **not** the host. The event loop is platform code and lives in L1.
L4 executes scripts and runs the per-frame body; L3 adapts between the C++
VM and the L2/L1 engine.

---

## 1. `crates/tjs` — the vendored C++ VM

`tjs` is the upstream C++ TJS2 VM, compiled through `build.rs` and exposed
through a thin Rust FFI. It is the compatibility anchor and the only legacy
crate the architecture still links.

| piece | where |
|---|---|
| the C++ sources | `crates/tjs/cpp/tjs2/` (~41 k lines: 37 `.cpp` + 39 `.h`) |
| the three bison grammars | `crates/tjs/cpp/bison/` |
| the ABI shim | `crates/tjs/cpp/tjs2_abi.cpp` + `tjs2_abi.h` |
| the port-authored C++ | `crates/tjs/cpp/streams.cpp` (the TJS stream IO) |
| the Rust binding | `crates/tjs/src/lib.rs` — the `tjs2_*` `extern "C"` surface |

The Rust side offers `Tjs2Engine`, the native-class builders
(`NativeClassBuilder`, `NativeInstanceBuilder`, `NativeStaticMembers`,
`NativeInstanceMembers`) and the value types (`TjsValue`, `RetainedValue`,
`ValueId`, `DetachedValue`).

**The ABI constraint that shapes L3.** The C++ ABI hands native callbacks
only the raw `tjs2_engine*` and exposes **no user-data slot**. That is why
`compat` keeps exactly one process-wide engine→context binding — see
[`l3.md`](l3.md) §7.

### Build dependencies

The VM build pulls in `zig` (C++ compiler plus package manager), `bison`
(the three generated parsers), `python3` (the date word map) and the C
**oniguruma** regex library, plus header-only `fmt`/`spdlog`/`boost` and
`libc++`. The whole set exists only to produce the VM.

## 2. `crates/vm` — the host

```rust
pub struct VmHost { /* the boxed C++ engine + the L3 CompatHost */ }

impl VmHost {
    pub fn with_default() -> Result<Self, VmError>;
    pub fn new(registry: PluginRegistry) -> Result<Self, VmError>;
    pub fn with_default_services(services: CompatServices) -> Result<Self, VmError>;
    pub fn engine(&self) -> &Tjs2Engine;
    pub fn compat(&self) -> &CompatHost;
    pub fn exec(&self, source: &str, name: &str) -> Result<TjsValue, VmError>;
    pub fn eval(&self, expression: &str, name: &str) -> Result<TjsValue, VmError>;
    pub fn tick(&mut self, frame: FrameCtx<'_>) -> Result<(), VmError>;
}
```

`VmHost` owns:

* the `Tjs2Engine`, boxed so its address stays stable for the L3 binding;
* the `CompatHost` that holds the native surface state;
* the `EventAdapter` that turns platform events into script events;
* the per-host log deduplicator.

**Drop order matters.** The fields are declared so the engine is dropped
last: the dispatch state retains values whose `Drop` releases an id on the
engine, so the state must be released while the engine is still alive. The
`Drop` impl calls `compat.shutdown()` first, flushes the final log summary,
and only then detaches the log callback.

### The services seam

The L2 service handles are **not** owned by the VM host. The composition root
attaches them through `CompatServices` **before** the surface is installed,
so a plugin that reads a service at registration time finds it.

### The frame body

```rust
pub struct FrameCtx<'a> {
    pub now_ms: u64,
    pub dt_ms: u32,
    pub body: &'a mut dyn FrameBody,
    pub events: &'a [PlatformEvent],
}
```

`VmHost::tick` is the whole per-frame body:

1. `begin_input_frame` — clear the per-frame input state;
2. for each platform event: apply it to the input state, then map it to a
   TJS event and dispatch it;
3. `end_input_frame` — commit, so the held/repeat counters advance exactly
   once;
4. `run_frame_body(body, &mut ctx)` — drain the timer posts, then the sound,
   video, async-trigger, continuous-handler and movie/transition polls.

Each segment reports its wall-clock cost through the `FrameBody` hooks, which
is how the composition root attributes a slow frame.

The engine owns the clock: `VmHost` receives `now_ms`/`dt_ms` from the
engine's frame and never accumulates a delta of its own.

### Logging

The engine's log callback routes through the `log` crate. The host
deduplicates repeats: the first few full exception dumps are emitted in full
(the first is the root-cause evidence), then a suppression summary with the
running count and the last timestamp is emitted instead. The full dump count
is 3.

## 3. Script execution and loading

`Scripts.execStorage`/`evalStorage` read the named script through the L2
storage and offer the raw bytes to the TJS2 **bytecode loader first**; only
when the loader reports the input is not bytecode is it decoded as text,
which is the reference's order. Text decoding handles the `FE FE` cipher /
zlib container, a UTF-8/UTF-16 BOM, an explicit `Scripts.textEncoding`
override, then UTF-8 and CP932; an undecodable script raises a typed error
instead of producing mojibake.

`compat::exec_storage(engine, storage, name)` is the core of
`Scripts.execStorage` without the native wrapper; the composition root uses
it to run the startup sequence.

A caught script error is formatted as `<block>(<line>): <message>`, so a
host-side failure names the failing script and line instead of only the raw
message. The throw-time stack is the script `Exception` object's `trace`
member; `Scripts.getTraceString()` returns the *current* (catch-site) stack
instead.

## 4. The TJS2 language, as the VM implements it

TJS2 is a C-family embedded scripting language with its own semantics. It
looks familiar — `var`, `function`, `if`/`for`/`while`/`switch`,
`try`/`catch`/`finally`, `this`, `new`, `class … extends … super`, object
and array literals, `typeof`, `instanceof`, `in`, `with`, `delete` — but the
grammar and the runtime diverge enough that no JavaScript engine can run it.

Reserved words that JavaScript does not have: `int`, `real`, `string`,
`octet`, `getter`, `setter`, `property`, `global`, `incontextof`,
`isvalid`, `synchronized`, `goto`, `enum`, `public`/`private`/`protected`/
`static`, and `NaN`/`Infinity` as keywords.

Notably absent compared with JavaScript: `let`, `of`, arrow functions,
template strings, destructuring, spread, generators, `async`/`await`, and
`undefined`.

Semantic differences that break real scripts:

* an explicit **int/real** numeric split — integer division, overflow, bit
  operations — where JavaScript has only doubles;
* the **`octet`** binary-buffer type;
* explicit **`getter`/`setter`/`property`** declarations and Java-style
  class access modifiers;
* **`incontextof`** (this-rebinding call), **`isvalid`/`invalidate`**
  object-lifetime calls, **`global`**, **`synchronized`**;
* a different **`typeof`** result set and a different standard library
  (`Array`, `Dictionary`, `RegExp`, `Date`, `Math`, `Octet`, …) with a
  **`delegate`** mechanism.

The TJS spellings matter for every script: `typeof` yields `"Object"`,
`"Integer"`, `"Real"`, `"String"`, `"Octet"` or `"void"`. Only an **absent**
member yields `"undefined"`; a present-but-unset member is `"void"`. `void`
is not `undefined`, and a bare `undefined` raises.

## 5. The TJS2 VM's architecture

The VM the port replaces is the upstream C++ TJS2 engine, mirrored in
`crates/tjs/cpp/tjs2/`. Its reference source is `reference/cpp/core/tjs2/`:
58 files and 3 bison grammars, 37 304 lines. This section is the map a
port reads; §6 is the port's own plan.

### 5.1 The pipeline

```
source (.tjs)
  |
  +-- lexer                      tjsLex.cpp          1 895 lines
  +-- preprocessor               bison/tjspp.y         115 lines
  +-- parser  (bison)            bison/tjs.y           861 lines
  |     +-- AST of tTJSExprNode tjsInterCodeGen.h
  +-- code generator             tjsInterCodeGen.cpp  4 120 lines
  |     +-- tTJSInterCodeContext
  |           +-- code array      tjs_uint32[]
  |           +-- register array  tTJSVariant[]
  |
  +-- interpreter                tjsInterCodeExec.cpp 3 109 lines
  |     +-- tTJSInterCodeContext::ExecuteCode(ra, startip)
  |
  +-- or -> bytecode writer        tjsByteCodeLoader.cpp 743 lines
        +-- a TJS2100 file
```

A date literal is parsed by its own path: `tjsDateParser.cpp` with
`bison/tjsdate.y`.

### 5.2 The execution model

The VM is a **register machine, not a stack machine**. The registers are
`tTJSVariant` slots and the code is an array of `tjs_uint32` words; both
addresses are scaled by the element size
(`tjsInterCodeGen.h:34-41`):

```
TJS_TO_VM_CODE_ADDR(x) ((x) * sizeof(tjs_uint32))
TJS_TO_VM_REG_ADDR(x)  ((x) * sizeof(tTJSVariant))
```

The opcode set is ~105 entries in `tjsInterCodeGen.h`: `VM_NOP`,
`VM_CONST`, `VM_CP` (copy), the comparisons `VM_CEQ`/`VM_CDEQ`/`VM_CLT`/
`VM_CGT`, the truth tests `VM_LNOT`/`VM_NF`, the jumps
`VM_JF`/`VM_JNF`/`VM_JMP`, and the arithmetic and logic family. Each
member of that family has a property-accessor variant, generated by the
`TJS_NORMAL_AND_PROPERTY_ACCESSER` macro, so `a.b += 1` is one opcode
rather than a get-modify-set sequence.

`try`/`catch` is **inside** the VM: the code generator's `tNestType`
lists `ntTry` and `ntCatch` beside the loop kinds, and the executor has a
separate `ExecuteCodeInTryBlock` entry. A script `throw` and a host error
share one channel, so the port's exception model must match at the value
level, not just in its message.

### 5.3 The value model

| type | where | what it decides |
|---|---|---|
| `tTJSVariant` | `tjsVariant.h` (1 286) / `.cpp` (1 281) | the tagged union: void, integer (`tjs_int`), real, string, octet, object — reference counted |
| `tTJSVariantString` | `tjsVariantString.cpp` (1 048) | **code-unit** based: the text is an array of `tjs_char` (UTF-16) with a short/long string optimisation. An empty string is a null pointer (`tjsVariantString.cpp:561-565`) |
| `tTJSVariantArrayStack` | `tjsInterCodeExec.h` | the register allocator: a pool of `tTJSVariant` arrays, handed out and released in stack order |

The string representation is the single largest semantic trap for a Rust
port. `length`, `charAt` and indexing count **code units**, not bytes and
not scalars; a Rust `String` is UTF-8 and cannot answer those questions
without an explicit definition.

### 5.4 The object model

The central interface is `iTJSDispatch2` (`tjsInterface.h`):
`FuncCall`, `PropGet`, `PropSet`, `Compare`, `IsAssignable`,
`NewInstance`, `IncrRef`, `DecrRef`, `InstanceOf` — **each in a
by-name and a by-number form** (`FuncCallByNum`, `PropGetByNum`,
`PropSetByNum`, `PropSetByVS`). A member name is resolved to a number
once and the number is cached as a *hint*; the by-number path is then the
fast path. A port that offers only by-name lookup is not the same VM, and a
port that resolves names differently is not compatible.

The class hierarchy:

| class | where | role |
|---|---|---|
| `iTJSDispatch2` | `tjsInterface.h` | the interface every dispatchable implements |
| `tTJSDispatch` | `tjsObject.h:85` | the base: refcount and `BeforeDestruction` |
| `tTJSCustomObject` | `tjsObject.h:258` | the script-object base |
| `tTJSExtendableObject` | `tjsObjectExtendable.h` | adds the extendable (member-table) behaviour |
| `tTJSNativeClass` | `tjsNative.h:178` | a native class: `RegisterNCM`, `CreateNativeInstance`, `CreateBaseTJSObject` |
| `tTJSNativeInstance` | `tjsNative.h:35` | the native instance protocol: `Construct`, `Finalize`, `SetInstanceType` |
| `tTJSNativeFunction` | `tjsNative.h:479` | a native function object |

The member and class semantics are the subtle part: a script `class` copies
its member table into the instance, so a member written on the class is
**shared by every instance of it**. The title-entry animation defect is an
instance of exactly that — the game's `AffineSourceMotion` keeps
`_innerStorage` on the class, so the load order of the game's motions
decides whether the title animates. Lookup order, `delegate`, `extends`,
`with` scoping, getter/setter invocation and the exception hierarchy all
have to match exactly.

### 5.5 The standard library that lives in the VM

`Array` (1 884), `Dictionary` (808), `RegExp` (763, oniguruma), `Date`
(357) and the date parser (225), `Math` (465), `OctPack` (1 045), the
binary serializer (424/518), `Exception`/`Error`, the MT19937 random
generator (360), `Namespace` (233), the const-array data (335), the global
string map (122) and the shared helpers in `tjsUtils.h` (697).

### 5.6 The bytecode format

`tjsByteCodeLoader.h` defines the container: the file tag `TJS2` and the
version `100` (both little-endian `tjs_uint32`), then the `OBJS` section
(the object dictionary), the `DATA` section (the const arrays) and the code
and register sections. A compiled script starts with the bytes `TJS2100`.

A port must decide whether it has to **load** this format. The shipped
game ships `.tjs` sources, and a port could use its own IR — unless a
title ships precompiled bytecode, in which case the loader is mandatory
(§6, risk 4). Our own writer has a known defect in this area:
`compileStorage` does not round-trip a `+=` or `++` statement, because
the writer's `TranslateCodeAddress` registers only the base opcode of each
arithmetic family while the loader multiplies the exported offsets again
(`TODO.md` §12).

### 5.7 The seam the Rust side uses today

`crates/tjs/cpp/tjs2_abi.h` is the C ABI we wrote over the upstream VM:
engine create/destroy, compile, exec/eval, the retained-value registry and
the native class/instance registration. `crates/tjs/src/lib.rs` is the safe
wrapper over it — `Tjs2Engine`, `TjsValue`, `RetainedValue`/
`DetachedValue`, `TjsError`, `NativeClassBuilder` and the native instance
builders.

Two properties of that seam are load-bearing and a port must keep them:
the engine owns the VM's global state, so **there is one VM per process**
(the binding is process-global, and a second engine races it), and a script
exception's **original message** must survive the crossing unchanged.

## 6. The Rust port audit

**Deferred.** The Rust port of the TJS2 VM is not a first priority; the C++
VM stays until a real game runs end to end.

The feasibility audit is recorded in the migration design docs. The shape of
the conclusion:

* **A drop-in JS engine is impossible** — it is the wrong language.
* **Transpiling TJS2 to JS to run on QuickJS** needs a full TJS2 front-end
  *plus* emulation of TJS semantics, is strictly more work than porting the
  VM, and keeps a C dependency — the opposite of the goal.
* The resemblance **helps**: the parser is a familiar C-family recursive-
  descent/Pratt job and the VM is a register machine, so the syntax is not
  the risk — regex, string and class semantics are.

The largest components are the lexer (~1 900 lines of C++), the three bison
grammars, the interpreter code generator (~4 100 lines) and the bytecode
executor (~3 100 lines). The object model, the variant/string handling, the
binary serializer, the bytecode loader and the date parser follow.

The hard parts, in order of risk:

1. **Regex parity.** TJS uses oniguruma semantics — backreferences,
   lookaround, `\p{}`. A backtracking engine is the closest match but is not
   oniguruma-exact; a C library can stay behind a feature as the escape
   hatch.
2. **String semantics.** TJS strings are code-unit based with specific
   comparison and member-name rules; a UTF-8 representation must define
   indexing and `charAt`/`length` to match TJS, not Rust.
3. **Member lookup and class semantics.** The lookup order, `Class`/
   `delegate`/`extends`, `with` scoping, getter/setter invocation and the
   exception hierarchy are subtle, and scripts depend on them.
4. **Bytecode / OctPack.** Internal, so a port could use its own IR — unless
   a title ships precompiled bytecode.
5. **Number formatting and the date parser.** Byte-exact outputs scripts may
   compare.

The estimate is ~35–40 k lines of Rust plus a conformance corpus: a
multi-week/month project, not a refactor. The recommended sequence is a
differential harness first (the same script on the C++ VM and the Rust VM,
comparing value dumps and errors), then a bottom-up port: variant/string/
object model and native registration → lexer → parser/AST → compiler/IR →
VM → the standard library.

## 7. Known gaps in L4

* **`unsafe impl Send + Sync for Tjs2Engine` is unsound as a public API** —
  two engines would race the process-global VM state — and nothing requires
  the bounds.
* **`compileStorage` does not round-trip a `+=` or `++` statement.** The
  writer's code-address translation registers only the base opcode of each
  arithmetic family, so the add/increment variants export code-generator byte
  offsets that the loader multiplies again. Loading a game's `.tjsb` is
  unaffected, because the reader's translation is the one that runs there.
  The open question is whether the shipped engine shares the snapshot's
  incomplete export table; it needs a `.tjsb` from a shipped writer containing
  an `+=`-family or `++`/`--` statement to settle.
* **The TJS stream IO bypasses Rust.** `cpp/streams.cpp` implements TJS
  `Array.save`/`load`/`saveStruct` with `std::fopen` directly. It is the
  only port-authored C++ besides the ABI shim, it is the one IO path the
  stateless fs surface cannot reach, and every save-path memory-safety
  defect found so far was in it — including a serializer that recurses
  without a depth bound.
* **The Rust port of the VM is deferred**, so the build keeps the zig/bison/
  python/oniguruma dependency set and the Android VM build stays the fragile
  part of the Android story.
* **`docs.old/vm-defects.md`** records the VM and reference defects a rewrite
  must not rediscover.
